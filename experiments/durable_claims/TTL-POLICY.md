# AUD-94 — Ownership TTL and delivery deadline

Proposed integration policy; no production settings or retry policy changes.

The server's 60-second claim TTL and P2's 50-second delivery deadline serve different purposes. The former bounds ownership eligibility after a worker disappears; the latter bounds how long one client delivery operation waits. Neither timeout proves the recording was lost or the provider stopped.

1. Keep TTL=60 seconds, server database clock only. Keep P2's existing 50-second wall deadline and hard cap of three audio sends. No heartbeat or longer deadline is introduced by this optimization.
2. Before the client deadline, a duplicate live operation returns processing; completed operations return the canonical attempt. Processing-status reads send no audio and start no provider work. A live claim is never stolen merely because the browser timed out, backgrounded or disconnected.
3. At the client deadline, end automatic delivery, preserve the in-memory recording, and disclose that delivery is unconfirmed. Do not report a definitive failure, replay the question or start another recording automatically. Expiry of a client timer never grants ownership.
4. Explicit **Send again** should first read the owner-scoped operation status. Complete: adopt the canonical result. Live: offer bounded status recovery within the new user-authorized operation's ordinary deadline, without audio resends. Expired/cancelled without a result: disclose that resending is required; the next explicit resend reacquires the same operation ID with a higher fencing token. Polling itself never claims or invokes STT. Missing/unreadable/ambiguous evidence stops recovery conservatively.
5. At or after server TTL expiry, a legitimate retry can acquire a higher token, after the same transaction/state/owner checks. Old results cannot overwrite its work. A finalization validated before expiry while holding the owner lock may finish its short transaction after the timestamp; a contender must wait, then read its committed result or a fresh claim. TTL is not a destructive row deletion timer or a promise of commit by that instant.
6. If the original worker dies before durable transcription, safe takeover occurs after TTL, not necessarily inside the original 50-second delivery window. This may require manual recovery. Raw audio remains in client/server memory only. After reload, status can recover a saved result; if no result exists and the Blob is gone, disclose that and require an explicit new recording.
7. Takeover can repeat external provider work whose result was lost before persistence. Exactly-once persisted acceptance is enforced; exactly-once provider billing is not promised. Provider/memory budgets and limits on repeated recovery need review before full migration.

Implemented here: unchanged TTL, expiry/fencing, typed processing status, no-provider status reads, unchanged P2 cap/deadline, and deterministic 50/59.999/60-second boundary tests. The local benchmark's existing experimental 202/status adapter remains unchanged except numeric profiling headers. Production-client status-first Send again, disclosure and UI integration are **not implemented** or activated by this pass.
