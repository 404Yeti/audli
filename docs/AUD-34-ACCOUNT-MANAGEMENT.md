# AUD-34 account management

Settings → Account & Data provides permanent deletion for signed-in PostgreSQL accounts and a separate onboarding restart for development or operator-authorized test accounts. This PR is based on the AUD-33 revision of main and introduces no AUD-32 changes. **Release review is blocked; see [AUD-34-RELEASE-REVIEW.md](AUD-34-RELEASE-REVIEW.md).** No deployment, production deletion, or paid AI request is part of verification.

## Inspected inventory (2026-10-12, read-only)

The connected Audli Supabase project has migrations 001–003, application tables in `public`, and managed Auth tables in `auth`. There are **zero Storage buckets, objects, multipart uploads, and multipart parts**. Learner recordings exist only during validation/transcription and are not intentionally retained by the application; temporary decode files are removed on normal request exit. Recognized text, attempts, evidence, conversations, lessons, profiles/preferences and generated audio blobs are stored in the application database. `exercise_audio` is an ephemeral generated-audio cache, restored from owned database blobs; it is not learner recording storage. No external media or payments were found. **ElevenLabs retains generation history by default; learner-specific generated text/audio is an external resource not erased by this implementation.**

Application foreign keys use NO ACTION, so deletion explicitly orders children before parents: evidence, turns, assessments, adaptation/evaluation records, conversations, follow-ups, coaching-audio references, lesson/exercise links, attempts, exercises, lesson lifecycles, sessions, generated-audio blobs, profile and application user. Auth identities, sessions, MFA factors/recovery codes/challenges, one-time tokens, OAuth grants/consents, and WebAuthn rows cascade from `auth.users`. Refresh tokens also cascade from sessions, but legacy refresh rows can lack that link; these are explicitly removed by verified owner UUID. `auth.flow_state` has a user UUID without a cascading FK, and SCIM mappings SET NULL; both are explicitly removed for that owner.

## Trusted deletion and failures

FastAPI verifies the bearer with Supabase Auth. Deletion binds that verified JWT's session ID to a live `auth.sessions` row owned by the request user, then asks for the current password **every time** and verifies it with the publishable Auth endpoint using the server-fetched email. The resulting identity must match the request owner. Local revocation of its temporary session is attempted and it is never returned to the browser; successful deletion also removes every Auth session transactionally. If both logout and deletion fail, the undisclosed temporary token expires under Auth policy. Current product sign-in is email/password. Verified MFA factors in either the original user or password response refuse deletion; the original-factor check happens before password login. The message/link uses the existing product contact `robbie@audli.ai`, tells users to keep MFA enabled, and forbids sharing passwords/recovery codes. There is no implemented support-assisted MFA verification workflow; operator readiness is a release prerequisite.

Deletion runs using the existing trusted backend PostgreSQL connection, **not** a browser Auth admin request or a browser privileged key. It explicitly revokes all refresh tokens/sessions and deletes `auth.users` along with application rows in one transaction. This deliberately avoids an Auth-admin HTTP/SQL two-system partial commit. No new service-role key or public database function is introduced. The backend database role must have SELECT/DELETE access to the listed Auth tables, UPDATE on `auth.users` for its row lock, SELECT on `storage.buckets`, and existing application table privileges. A read-only connection using the existing private operator/backend configuration verified these capabilities as `postgres`; `anon`, `authenticated`, and `service_role` have no direct SELECT/DELETE grant on the listed Auth tables. The connector cannot read Render's database environment value, so equality with the deployed credential remains unverified. Do not grant administrative capabilities to browser roles. Missing privileges/changed managed schema fail with a retry/support error, not success. There is no schema migration in this change.

Authenticated PostgreSQL mutations across API processes share a transaction-scoped advisory lease keyed by verified user UUID. A separate NullPool connection holds the lease across provider awaits without consuming the application pool; its idle transaction timeout is disabled only for that lease transaction. Contending operations retry for about five seconds before returning a retryable conflict. Auth-user existence is checked under that same lease before learner initialization, preventing stale-but-previously-verified requests from recreating deleted application users. Reads release the lease after initialization; previously downloaded content cannot be clawed back. All API instances must use the same writable database. Back-end operator scripts must not mutate an account concurrently outside this protocol.

Cache files are deleted before the database transaction commits. Failure to remove a file, an unsafe filename/symlink, ownership conflict, or any database/FK failure prevents success and rolls back database deletion. A removed cache can be regenerated from the still-retained blob after rollback. Successful deletion commits before returning `deleted: true`; only then does the UI sign out, clear local credentials and discard private state. If the response/commit acknowledgment is lost, the UI says deletion could not be confirmed; a later authenticated read/sign-in resolves whether the account still exists. Duplicate deletion after success is rejected as unauthenticated.

If **any Storage bucket appears**, deletion refuses without deleting account data. SQL deletion of `storage.objects` alone does not remove physical objects; adding Storage requires an audited Storage API purge/retry design before enabling this flow again. This is a fail-closed architecture guard for the inspected no-Storage deployment.

Completed accent usage reservations are deleted. Outstanding failed/unknown provider leases are assigned a random scope with no remaining account/lesson link, preserving their concurrency slot until expiry. Aggregate spent-character counters remain so deletion cannot reset shared spending controls. They contain no learner identity, content, or audio.

## Restart onboarding

`AUDLI_ONBOARDING_TEST_ACCOUNTS` is a server-controlled JSON list of UUIDs, default `[]`. Only the listed authenticated owners can reset in production; development environments allow reset. Browser metadata, UUID fields and frontend visibility do not authorize it.

The confirmation lists the exact reset: preferred name, English target-language choice, goal, interests, target situations, accent preferences, initial onboarding snapshot, and onboarding answers/recognition/checkpoints. Account/Auth identity, lessons, attempts/evidence, scores, difficulty, completed-attempt count, and browser accessibility choices remain. Initial snapshot is cleared; existing learned scores remain intentionally intact.

An open lesson (active **or paused**) or incomplete exercise blocks reset. Finish it first. Reset checks a locked profile revision and uses the account lease/global local route lock to avoid an active save race. It increments rather than reuses onboarding/question revisions, restores the introduction/status welcome, removes the prior typed-name marker/pending speech, and reloads into the same voice/typed-name onboarding flow. Repeated resets work; stale pre-reset submissions conflict.

## Retention and limitations

No legally required retention exception has been identified or configured in Audli; this code does not invent one. Managed Auth audit records, infrastructure/provider records and private backups are not erased by this control. Five nonempty private database dumps and three empty export files were found, with no documented expiry. Their retention is not bounded by a verified policy. [Release review](AUD-34-RELEASE-REVIEW.md) separates confirmed periods, published defaults and unknown settings. Confirmation discloses retained copies without claiming they necessarily expire. Restoring backups must not re-enable deleted accounts or publish historical data; an independently retained deletion record and tested reconciliation are still missing.

The local cache is ephemeral; same-host workers share its path. Render inspection confirmed one API instance and the Dockerfile specifies one worker. Overlapping deploy instances or future independent filesystem replicas still need coordinated cache purge/expiry before promising physical removal on every replica. Deleted users cannot access residual cache files because all audio reads require verified account ownership and retained DB records. No production account was deleted during development. MFA and future Storage refuse self-service deletion; multi-host purge remains an architecture limitation.
