# Physical iPhone Safari acceptance — proposed, not authorized to run live

Prerequisites: separately approved environment/activation and provider budget; authenticated owner test account; current deployed revision/protocol/flags verified; rollback operator available. Automated WebKit is not a physical acceptance result. Do not change codec, model, retry timing, CORS or routing for these tests.

Record each case with: random upload ID, random operation ID if issued, number of actual audio POSTs, elapsed wall-clock milliseconds, status-read count, recovery category, whether the original recording remained available, resulting phase/revision delta and duplicate-call counts. Keep IDs in restricted short-lived test notes; never export account IDs, tokens, private text, audio or full request bodies. Use numeric server stage counters and existing sanitized telemetry. Do not export a full HAR: authorization and multipart bodies may be present. Device screenshots should omit private spoken text and account details.

1. Normal Wi-Fi: finish a lesson from check-in through exercise/follow-up, feedback, closing and completion. Each recording has one accepted attempt; each final assessment has one evaluation/adaptation event; completion survives refresh. Repeat a short portion on cellular.
2. Connectivity loss before receipt: start a recording upload, interrupt connectivity, restore it. Up to three actual sends in an automatic recovery run share one upload ID. No greeting/question replay or new capture happens automatically. Check-in revision ambiguity must stop instead of overwriting pending evidence.
3. Processing receipt/lost completion: after a 202 acknowledgment, interrupt status reads then restore. Send again reads the same operation first and sends no further audio while it is processing or complete. Matching complete result resumes once. Uncertain/expired/mismatched status retains audio and discloses uncertainty.
4. Explicit controls: Send again uses the original recording; Record again invalidates only the matching recording/question before listening; Replay question plays existing cached audio without new STT or TTS generation. Double taps produce one in-flight action.
5. Backgrounding: during upload and during status polling, switch apps then return to Safari. Automatic recovery stops, original audio remains in memory when Safari retains the page, and an explicit action resumes. No hidden resend or deadline reset is inferred.
6. Lock/unlock: lock during upload/status polling, unlock and return. Check the same retention/disclosure and operation-identity rules. If Safari evicts the page, treat it as reload, not preserved audio.
7. Reload: reload while upload or processing is uncertain. The previous session marker explains that the in-memory recording is unavailable before replay/capture. Restore canonical lesson/operation status; do not claim the answer was lost or accepted without evidence. No audio is persisted in IndexedDB/sessionStorage.
8. Cross-device/reset/expiry: while a mocked slow operation is active, reset or let the lesson expire. A late result cannot restore the old question or advance progression. Another account cannot read the operation result. Same-account competing operations receive a processing/conflict result and never start a second provider execution.

Pass: all state/recording invariants above; zero duplicate persisted progression/stale commits/owner leaks; no unexplained STT/TTS duplicates; no provider-wait database checkout; acceptable comparable latency/capacity; no Safari regression. Any invariant failure is a NO-GO and stops the test. Rare provider completion/crash windows must be identified separately from persisted duplicates, with honest recovery messaging.
