# Audli
Audli is a structured listening-comprehension platform. Eyes optional. Ears essential. AI works behind the scenes; it is never a conversation partner.

Two implementations coexist until 1.x is retired by a separate, approved change:
- **Audli 2.0** (this direction): `app/listening/`, `/api/listening/*`, `web/app/listening`, `web/components/listening`. Behind `AUDLI_LISTENING_ENABLED` (off by default).
- **Legacy 1.x** (the voice-first conversational tutor): everything else. It stays in production and its rules below stay binding for its routes. New work must not import from it, extend it or call its engine.

## Audli 2.0
Learner journey: Discover lesson → Listen → Optional transcript → Multiple choice → Spoken response → Fill in blank → Sequencing → Debrief → Success. Milestone 01 ships Listen → Optional transcript → Multiple choice. Milestone 02 (docs/LISTENING-M02.md) completes Spoken response → Fill in blank → Sequencing → Debrief. Success is still planned, not implemented; do not stub it in the UI.

- Lessons are generated or authored once, validated, published as **immutable versions** and reused. Edits publish a new version. Attempts pin the exact version (and audio variant) shown to the learner.
- Audio is audio-only by default. The transcript is optional, sentence-aligned, and delivered with the attempt. **Answer keys, explanations, rubrics, object-storage keys and checksums are never in a learner response before that learner has answered that question**; an explanation appears only for the question already answered. Enforce in response models and in tests.
- Exercises that can be scored deterministically (multiple choice, fill in blank, sequencing) are scored by application code, never by a model. AI is for generation, transcription and spoken-comprehension assessment only, and only in the separate worker process (`python -m app.listening.worker`) through durable PostgreSQL jobs with leases and fencing. Model ids, endpoints and request shapes for 2.0 live only in `app/listening/models.py`/`providers.py` (OpenAI SDK, strict structured output, `store: false`, retries off); no paid call without an approved plan (`scripts/listening_live_trial.py` refuses without one). The spoken-answer worker should run as its own least-privilege PostgreSQL role (`docs/postgres-listening-worker-role.sql`, `app/listening/roles.py`, tested in `tests/test_listening_worker_role.py`). Every 2.0 AI request first reserves its worst-case cost against the global daily ceiling and is refused when the kill switch is on (`app/listening/ai_budget.py`, migration 011, `docs/LISTENING-AI-SAFEGUARDS.md`); estimates are not billing, so a provider-side spend limit is required too. A model only classifies key points and quotes the learner; learner-facing text is built from the lesson's key points and verified quotes. The spoken answer is never part of a score; unreliable or thin evidence is unknown, never zero.
- Spoken recordings are validated, stored privately under `listening-tmp/` in their OWN store (separate bucket and credentials in production, separate folder locally; `build_recording_store`), never signed or served, and deleted as soon as the transcript is saved (or the job fails, or the sweep finds them). Only the learner's own transcript is kept.
- No conversational acknowledgments, turns, tutor voice or blocking AI call between exercises. Do not use `app.lesson`, `app.conversation`, `app.feedback`, tutor TTS or onboarding from 2.0 code (a test enforces this).
- Persistence: PostgreSQL in production, SQLite for local/tests, through SQLAlchemy Core on the existing engine. Tables are in their own `MetaData` (`app/listening/schema.py`) so the 1.x schema inventory, claims guards and account-erasure plan are unchanged. Learner rows cascade from `users`. Migrations 009, 010 and 011 (`docs/postgres-009.sql`, `docs/postgres-010.sql`, `docs/postgres-011.sql`, generated by `app/listening/migrations.py`; 009 is frozen) are additive and applied only by explicit operator opt-in (`python -m scripts.migrate_postgres --listening`), never at startup. It records itself in `listening_migrations`, **not** `schema_migrations`: 1.x treats `max(schema_migrations.version) >= 8` as the claims schema and refuses to start.
- Concurrency uses the database (unique constraints, a row lock on the attempt, idempotent writes: `client_request_id` for attempts, one immutable answer per question). 2.0 routes take no process-wide or per-learner lock and make no provider call.
- Audio bytes are never stored in PostgreSQL for 2.0. `app/listening/objects.py` provides private S3-compatible storage (production, required) and a local-filesystem store (development/tests only). Learners get short-lived signed URLs after an ownership check; local media links are HMAC-signed and are the only unauthenticated `/api` prefix.
- Learner recordings, when the spoken exercise lands, remain subject to "delete learner audio after transcription" below. Any retention beyond that needs an approved privacy and deletion policy first.
- Not approved yet (ask first): additional languages, teacher-authored lessons, payments, gamification, WebSockets, new infrastructure. Upstash Redis is approved for future rate limiting/caching only.
- Tests: SQLite always, plus a real PostgreSQL integration run (`AUDLI_TEST_POSTGRES_URL` pointing at a disposable cluster). Cover immutable publishing, learner-safe responses, answer-key isolation, scoring, idempotency, recovery, cross-account isolation, signed audio, alignment and the browser flow. Mock tests establish plumbing, not model accuracy.

## Safeguards that apply to both 1.x and 2.0
- No client secrets. Validate audio size, type, signature, decodability and duration. Delete learner audio after transcription; no raw audio logging.
- Local shared identity is development-only. Production requires server-verified Supabase Auth identity and request-scoped ownership; never trust browser learner UUIDs. Public deployment requires authentication and access controls.
- Preserve STT uncertainty. Unreliable attempts must not change learner state. Insufficient evidence is unknown, never a confirmed zero.
- Use strict typed schemas, small pure domain functions, explicit transactions and provider interfaces. Never mark work verified that was not run.
- Do not change the Supabase schema ledger semantics, production configuration or infrastructure without explicit approval.

# Legacy 1.x
The sections below govern the legacy conversational tutor and its routes. They do not apply to `/api/listening/*`, except the shared safeguards above.

## Architecture
Next.js/TypeScript client; FastAPI/Pydantic API; shared repository with SQLite for local/test persistence and Supabase/Postgres for production. Versioned PostgreSQL schema and setup live in docs/postgres.sql and docs/PERSISTENCE.md. Provider-specific generation, evaluation, speech and transcription live in app/services. Application code owns state, scores, adaptation and history.

## Product rules
- AUDIO FIRST, TEXT SECOND. Never expose scripts or expected answers before a successfully evaluated spoken attempt. Enforce this on the server, including debug endpoints.
- Evaluate meaning, not grammar or pronunciation. Distinguish missed from misunderstood information.
- Preserve STT uncertainty. Unreliable attempts must not change learner state.
- Change at most one primary difficulty variable. Maintaining difficulty within the learning edge or at bounds is valid. Persist explainable decisions.
- Original English only, one clear speaker. No external media, agents, payments, gamification or advanced difficulty dimensions.
- No client secrets. Validate audio size, type, signature, decodability and duration. Delete learner audio after transcription; no raw audio logging.
- Local shared identity is development-only. Production requires server-verified Supabase Auth identity and request-scoped ownership; never trust browser learner UUIDs. Public deployment requires authentication and access controls.

## Testing and conventions
Use strict typed schemas, small pure domain functions, explicit transactions and provider interfaces. Tests must cover .54/.55/.69/.70/.84/.85 boundaries, one-variable changes, bounds, state updates, schema rejection, uncertainty and transcript gates. Evaluator fixtures must include poor grammar with correct meaning. Mock tests establish plumbing, not actual evaluator accuracy.

## V0.2 spoken evidence loop
- Keep the v0.1 tag unchanged; reuse its generation repair, audio validation and recording helpers.
- Insufficient evidence is unknown, never a confirmed zero. Persist it separately from misunderstanding.
- Ask at most two voice follow-ups, only for insufficient evidence; choose progression in application code.
- Adapt only after the final assessment. If evidence remains incomplete, keep difficulty stable and audit why.
- Persist conversation turns/checkpoints. TTS failure must never roll back a completed assessment.
- Keep transcript gates in the backend; legacy evaluation cannot bypass an active V0.2 conversation.
- Spoken cues also have accessible text and replay controls; detailed metrics stay secondary.

## V0.2.1 terminal feedback
- Follow-up questions, evaluator notes and final feedback are separate conversational acts.
- Never speak evaluator notes directly. Compose terminal feedback from final evidence and the deterministic adaptation event.
- Validate the complete spoken message: at most three sentences and configured 30–50 word maximum; no questions, requests for evidence or numerical metrics.
- Unknown units never supply corrections. Unsafe/oversized correction labels use a complete safe alternative, not truncated prose.
- Version terminal-audio caches so previous evaluator-report audio cannot replay.


## Review v2 language coaching (AUD-77)
- Language coaching (grammar, naturalness, vocabulary) is advisory and may be generated only after a passage is successfully evaluated. It never changes scores, difficulty, adaptation, evidence or learner state.
- Keep comprehension accuracy and language coaching in separate lanes. Coaching input is the learner's own words only: never pass the script or expected answers, and preserve the learner's intended meaning, including factual mistakes.
- Saved responses are labeled "What Audli heard" and shown verbatim. Learner recordings stay browser-session-only; no server-side recording retention without an approved retention, privacy and deletion policy.
- Any corrected-answer synthesis stays behind a disabled flag with its own per-learner daily cap, independent of the daily lesson limit, and holds no account-wide lock across a provider call.

## Linear project management

Linear is the source of truth for project work.

Before using Linear:
- Confirm the Linear MCP server is available.
- If Linear is unavailable, continue the development task but report that Linear could not be updated.
- Never claim an issue was created, updated, or completed unless the Linear operation actually succeeded.

When starting a development task:
1. Search Linear for an existing issue that matches the task.
2. If an appropriate issue exists, use it rather than creating a duplicate.
3. If no issue exists and the work is substantial enough to track, create an issue in the appropriate Linear project.
4. Move the issue to In Progress when implementation begins.

During implementation:
- Keep the Linear issue aligned with material scope changes.
- Do not create issues for trivial fixes discovered while completing the current issue.
- Create a new issue for substantial newly discovered work that should be handled separately.
- Include the Linear issue identifier in the branch/commit/PR where practical.

When finishing:
1. Run the required tests and verification.
2. Do not mark the issue Done if verification fails.
3. Add a concise Linear comment summarizing:
   - what changed
   - important files/components changed
   - tests/verification performed
   - any remaining limitations or follow-up work
4. Mark the issue Done only after the implementation and verification are complete.

Never mark an issue Done merely because code was written.
