# Audli V0.2 — spoken listening companion

## Implementation plan and scope

Reuse V0.1 generation, bounded length repair, TTS provider, validated uploads, recorder lifecycle, transcription, transaction boundary and deterministic difficulty policy. Add a separate evidence assessment model, a small persisted conversation coordinator, reusable spoken cues and a quieter primary UI. Keep legacy result semantics and APIs available for old sessions. Never move the `v0.1` tag (original commit `3c182b16368daeac3b95d4a0dff4971831039b45`).

The slice is: listen → spoken summary cue → record → automatic transcription → check recognition → evidence assessment → zero to two spoken clarification questions → final assessment → spoken feedback and next step → adapted next clip.

Risks: semantic accuracy still needs teacher evaluation; schema correctness alone cannot prove it. A follow-up could be poorly worded despite schema validity, so inspect question quality during acceptance. Autoplay may be blocked: every cue has text and playback controls. Recording still needs localhost/HTTPS. Provider delays and failures must preserve turns and completed results.

## Evidence and scoring

Per expected information unit, V0.2 stores `demonstrated`, `partially_demonstrated`, `misunderstood`, or `insufficient_evidence`. Vocabulary is contextual semantic meaning; exact target wording and grammatical correctness are not required. Missing information in a free summary is unknown rather than contradictory. Evidence for observed understanding or misunderstanding must be a verbatim learner excerpt. Questions and original passage text cannot act as learner evidence.

The provider returns one required slot per unit. Non-unknown slots have one allowed learner excerpt and no question; unknown slots have empty evidence and a brief candidate clarification. Application code validates coverage and quote provenance and chooses follow-ups deterministically. Priority is main idea, details, vocabulary, inference. It asks at most one question per uncertain dimension and at most two questions total, never for an already confirmed misunderstanding. Later assessment receives all learner turns and their questions, allowing clarification to resolve earlier ambiguity. It never adapts on preliminary output.

Scores retain the V0.1 weights (.35/.40/.15/.10). Demonstrated is 1, partial is .5, misunderstood is 0. Unknown units are excluded, not assigned 0. A dimension with no observed units has a null score. The overall observed score uses available dimensions and is explicitly accompanied by weighted evidence coverage. If nothing is observed, overall is null. These are observed-evidence metrics, not claims about unobserved comprehension.

Once clarification ends, fully evidenced results use the unchanged V0.1 deterministic adaptation engine. If any units remain unknown, a deterministic compatibility rule holds difficulty stable, records why, and updates only fully observed profile dimensions. It preserves the previous overall profile estimate and unknown dimension estimates. Both branches complete the attempt and write an audit event with policy `v0.2-evidence`.

## State, persistence and compatibility

SQLite adds `conversations` and `coach_audio` tables, without altering or reinterpreting existing rows. The reference PostgreSQL schema is updated as well. Conversation state includes learner turns, selected questions, preliminary evidence and the pending recognized/confirmed answer. State names are LISTENING, AWAITING_SUMMARY, ASSESSING, AWAITING_FOLLOWUP, ASSESSING_FOLLOWUP, GIVING_FEEDBACK, READY_FOR_NEXT. LISTENING is the default before a conversation starts; recognizing a turn and processing media use explicit frontend sub-states.

The server checkpoints confirmed text before provider work. A reload during review or a failed assessment resumes that response and current question. Repeating an already processed turn returns the saved conversation, without another question or score update. Final evaluation, one adaptation event, profile update and final conversation are written in one existing repository transaction. Follow-up attempts remain linked learner responses; the summary attempt owns the single final result.

The transcript gate remains tied to that final completion. Legacy `/evaluate` rejects active V0.2 conversations so it cannot bypass outstanding questions. Public conversation responses never include the original script, expected answers, unit labels, preliminary feedback or raw evaluator judgments. They include only the currently issued conversational cue, learner-owned pending transcription and final result once completed. Earlier V0.1 feedback still loads, without converting historical missed scores to V0.2 semantics.

Audio bytes are not persisted for learner responses. A reload before transcription cannot restore an unsent browser Blob. Once transcription exists, its recognized/confirmed text is recoverable. Recoverable upload failures keep the local Blob until a usable response arrives.

## Spoken cues and UI

`AIProvider.speak` reuses the same OpenAI speech API and voice as exercise TTS; demo uses the same espeak path. Cue audio is cached locally and sanitized through the existing metadata-stripping decoder. Text is chosen server-side for the summary prompt, issued follow-up or completed feedback; the client cannot submit arbitrary speech text. Final speech appends a plain next-step description from the actual adaptation event, never numerical scores.

Audio generation is a separate request after a durable state transition. A voice-generation, decoding, serving or browser playback failure cannot roll back evaluation. Text and Continue remain available, with Retry audio. Playback controls handle browser autoplay restrictions. Coach audio does not autoplay into an active microphone recording. Detailed statistics and evidence states are behind “See details”; the transcript remains separately optional after completion.

The learner still explicitly checks recognition before assessment: stopping records and transcribes automatically, then “That’s what I said” confirms the recognized/corrected text. This small interaction is retained to avoid punishing speech-recognition errors.

## Chrome acceptance checklist

Run the backend and frontend as described in README, with OpenAI configured. Use a separate local test data directory for controlled research sessions if desired.

1. Generate and play an original clip. Before assessment, verify its transcript endpoint returns 403 and no client response contains the script or expected answers.
2. Hear Audli ask what you understood. If autoplay is blocked, tap its audio control; the same accessible text is visible.
3. Record a summary and stop. Expect automatic transcription, nonzero recording metadata, no empty-src warning, and a brief recognition check. Correct STT errors without repairing your spoken grammar, then confirm.
4. Give a comprehensive summary including meaning and reasons. Expect zero unnecessary follow-ups when evidence is sufficient. Try natural vocabulary paraphrases rather than repeating target words.
5. On another clip, omit a reason or vocabulary meaning. Expect a short relevant spoken clarification, not a premature zero. Transcript must still return 403 and adaptation must not yet be applied.
6. Answer correctly, confirm recognized text, and expect evidence to improve. Try an explicit incorrect answer on another clip: expect confirmed misunderstanding to remain distinct from unknown evidence.
7. Omit several dimensions. Expect no more than two questions. If evidence remains unknown, inspect “See details”: unknown scores are not 0, and difficulty stays stable with an audit reason.
8. Hear concise human feedback and the next step. Verify metrics are secondary and no numerical scores are read. Click “Show transcript” only now; its endpoint should return 200.
9. Continue and verify the next clip uses the final adaptation’s difficulty, changing at most one variable.
10. Force an assessment failure or interrupt connectivity after transcription, then reload. Expect the pending recognized/confirmed response and current question to resume; retry without duplicate questions or adaptation.
11. Simulate failed feedback audio. Expect text feedback, persisted results, available transcript, and Continue. Retry audio without another evaluation. Replay/stop cues and use Record again; prior object URLs must not play stale audio.
12. Deny microphone permission or fail upload. An existing local recording survives failed restart/upload; use the existing spoken-file fallback if needed.

Automated fixtures validate contracts, scoring and flow with prescribed AI responses. They do not establish real model accuracy or real-browser microphone/playback acceptance. Record manual observations before calling the spoken experience browser-verified.

The backend suite passes 131 cases, including every original V0.1 test. Frontend helpers pass 21 cases (6 API, 11 recording, 4 conversation-state/display). TypeScript and a production build pass. Next.js uses the TypeScript compiler API (`useTypeScriptCli: false`), preserving type checking while avoiding this environment's CLI subprocess returning empty `--showConfig` output. The complete-summary case passes: vocabulary paraphrase is demonstrated and no unnecessary follow-up is asked. The sparse-summary case also passes: initial vocabulary uncertainty stays insufficient evidence, two spoken follow-ups collect clarification, and final assessment/feedback persist successfully. These two real-provider checks were run separately; neither is a browser test.
