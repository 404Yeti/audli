# AUD-94 migration safety and recovery review

> Historical stage evidence. Current integrated deployment and rollback authority: `docs/AUD-94-RELEASE-CANDIDATE.md`.

This review builds on `4e5ed23`. No production activation is approved. The native application does **not** import the installer: `experiments.assessment_claims.integration.install()` requires demo/mock providers, a disposable loopback PostgreSQL database and an explicit ownership mode. Existing benchmark JSON and results are immutable regression evidence; these safety changes have not been assigned the old benchmark's latency numbers.

## Client contract

HTTP 202 is processing, not a recognized recording. It contains a canonical operation UUID and kind. P2 remembers that receipt with the in-memory Blob, polls an authenticated status endpoint without additional audio sends and adopts only matching identity and a complete result. Unknown/expired/mismatched status stops recovery and retains audio. Explicit Send again reads the retained receipt first, even if retry policy has since been disabled. Every automatic recovery retains its original three-send cap and wall-clock deadline. Hiding or leaving the page aborts status recovery; no background resend is invented. Reload retains the existing disclosure marker, never audio or transcripts. A reload does not imply delivery failure or permit claim takeover.

The existing check-in revision reconciliation is unchanged for failures without a receipt. An unrelated revision or matching text cannot prove delivery. A check-in receipt binds the exact recording, route, canonical multipart bytes/fields and server-verified owner. Send again does not advance the revision or overwrite ambiguous pending evidence.

Record again is an explicit action. After reading the current lesson, a capability-aware client invalidates its known recording operation, or CAS-clears the current exercise's pending attempt/question. Captured evidence rows remain; a completed assessment cannot be undone. Older servers return 404 for capabilities and retain their prior flow. Network uncertainty during this check preserves the old recording. Replay question uses the existing audio cache and is independent of claim takeover.

## Remaining provider-backed routes

The local compatibility installer preserves the original route implementations and validation for generation, onboarding, check-in extraction, planner, homework/review, recognition/TTS and voice previews. A shared account slot is acquired **before** handler/provider entry. Each short database transaction checks owner, status, fencing token and server-clock expiry; both ordinary repository transactions and direct engine connections participate. Read-only AUTOCOMMIT connections retain their original write guard. No database connection is held just to retain ownership during provider awaits.

Native assessment/final progression remains the atomic specialized implementation. Compatibility handlers can have several legacy checkpoints and external effects: their success receipt is saved after handler transactions and before a small JSON acknowledgment. A crash in that gap is **uncertain**, never an automatic provider rerun. An expired compatibility claim is quarantined; expiry alone does not steal it. Only an error proven to precede both writes and provider entry releases its slot. This conservative behavior is deliberate, but universal automatic crash recovery is **not complete**. Converting these remaining handlers to native stage-specific atomic receipts is a production gate.

Compatibility JSON buffers are capped at 1 MiB; request audio memory is capped at the existing audio limit plus 64 KiB multipart overhead. Handler execution is bounded at 55 seconds inside the existing 60-second claim TTL. No retry-policy timeout is changed. Original non-JSON/audio response transport is preserved. Buffered audio/file responses with a known content length finish their already-completed provider/cache receipt before headers, preventing a fast-following assessment from racing admission cleanup. Genuine unbuffered streams retain ownership through their body; no provider work is moved behind an acknowledged receipt. A repeat of an identical streamed-operation key is refused; the explicit audio replay action starts a fresh request that uses the original cache. It never replays JSON as audio. If a stream is interrupted, ownership stays quarantined until its canonical outcome can be resolved.

A provider can finish before a worker crash loses its unpersisted result. Exactly-once external billing is not generally possible. Exactly-once persisted assessment/progression remains fenced and transactionally unique.

## Closing, reset and expiry

Original lesson projections and heard/closing/homework handlers remain in use. Closing acknowledgment persists COMPLETED exactly once; receipts cannot replay across a changed profile/lesson/conversation checkpoint. Reset invalidates known active claims, rotates the fence and runs the original revision/allowance/reset transaction together, including lessons without an exercise. A stale revision rolls back invalidation as well as state changes. Expiry/closing settlement takes the same owner lock and atomically invalidates stale provider ownership before its original state mutation. Late writes are refused. A confirmed onboarding restart keeps the pre-existing explicit discard semantics for unevaluated work; ordinary recovery never deletes evidence.

Self-service account deletion is deliberately blocked in the local installer until the erasure/drain protocol is reviewed. Operation tables have not been added to the production erase plan. This is a release gate, not a production change.

## Schema and security review

The PoC schema is **not a production migration**. A future additive, versioned migration must separate internal processing records from public Data API access, use a dedicated non-owner backend role, fixed function search paths, explicit EXECUTE grants, RLS and immutable owner/FK constraints. `security.py` rehearses denial of PUBLIC/anon/authenticated/service_role table/function access, FORCE RLS and explicit non-bypass server-role policy on local operation tables. Browser roles cannot gain access by setting claim GUCs. Backend DB credentials are trusted and never sent to browsers; owner authorization still comes from Supabase Auth and owner-scoped lookups, not editable claims or browser UUIDs.

All existing learner tables have live-operation guards and cross-parent owner checks. Deferred checkpoint-parent validation preserves conversation-before-followup insertion order and rejects invalid parents at commit. A transaction-local GUC is fencing context for trusted backend code, **not** an authentication credential. The current backend role's direct table privileges and ability to disable triggers must be reduced during production role design. Function execution revocation is insufficient if untrusted roles retain direct DML or schema CREATE rights.

Before writing a production migration: inventory actual Supabase default privileges, exposed schemas, schema CREATE grants, RLS policies, backend-role memberships and authenticated/service_role inheritance. Rehearse upgrade, role-restricted real routes, restore, account erasure, tombstone retention and downgrade against a production-shaped sanitized schema. Do not install the PoC's `poc_*` objects into production.

References reviewed: Supabase [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [roles](https://supabase.com/docs/guides/database/postgres/roles), and changelog (including pending PostgreSQL maintenance notices). No production database was queried or altered for this review.

## Guard-aware bridge, deployment and rollback

1. Ship a reviewed additive schema and a **guard-aware bridge** only after separate approval. Bridge workers retain the old advisory lease but use the same durable slot/fences. Claims-only workers take the same advisory key briefly during admission. The lease-exemption decision is per middleware instance, so a claims-only worker cannot silently exempt a legacy bridge in the same process/test.
2. Unaware old workers must be drained before enforcement/activation. Database guards prevent stale persistence, but cannot prevent an unaware worker calling a provider after reading state. Do not claim that row triggers alone make unaware mixed fleets safe. Claims-only installation explicitly rejects a declared nonzero old-worker count; fleet verification is an operational gate, not an automatic discovery feature.
3. Confirm no old requests, active advisory leases or unknown operation formats; verify capacity for overlapping aware workers, then separately approve a bounded canary. Do not enable pooled leases, change recording recovery policy, providers, codecs, CORS or routing.
4. For rollback, stop new claims-only admission, wait for finite active claims or fence/invalidate them through an owner-locked recovery transaction, and resolve unknown commits from canonical attempts/evaluations/lesson revisions. Return only to guard-aware bridge code. Keep operation receipts, guards and learner evidence. Never roll back to an unaware binary while claims can exist or drop ownership records to restore traffic.
5. Quarantined compatibility operations require explicit domain recovery: recording replacement, CAS reset, expiry or reviewed reconciliation. Do not blanket-expire-and-retry assessments, generation or external homework actions. Monitor their age/count; this remaining recovery UX must be completed before activation.

The prior five-connections/worker projection applies only after complete lease removal and excludes other clients; two aware workers project ten plus other traffic against fifteen Supavisor backends. Bridge workers still retain long leases. Recheck actual utilization and overlap; two hundred pooler clients is not two hundred backend slots.

## Activation criteria and monitoring

GO only when all native and compatibility writer/recovery cases, role-restricted schema rehearsal, account erasure/retention, remote required CI, Chromium/WebKit and physical iPhone acceptance pass; no stale commits/duplicate progression; no provider-wait checkouts on migrated paths; unchanged P2 send cap/IDs; and current production headroom is verified. Current recommendation remains NO-GO activation.

For a future separately approved canary: baseline connection count and keep at least three of fifteen backend slots free; stop if app+other sessions reach twelve persistently or any pool timeout occurs. Investigate p95 pool wait above 500 ms or request p95 worsening over 20% against a comparable baseline. Any stale-worker commit, duplicate evaluation/adaptation/progression, lost recording without disclosure, owner mismatch or persistence failure immediately stops admission and triggers guard-aware rollback. Track numeric counts, random upload/operation correlation IDs, stage timings and categorical outcomes only; never capture audio, transcripts, tokens or account IDs in monitoring artifacts.

Local drain certification is implemented in `recovery.py`: it returns numeric processing/unresolved/unknown counts and refuses rollback to an unaware protocol or while any count is nonzero. It does not stop traffic or detect unreported old binaries. Deterministic tests cover active, expired, recovered and unknown-format ownership.

## Lost acknowledgments and unreliable recognition

Explicit replacement tombstones the exact stable recording ID before discarding audio, including a recording whose request body is still arriving. A status-404 is never used as proof that no old request can arrive. The replacement endpoint checks the current question/pending evidence or check-in revision, rotates fencing and records an idempotent replacement marker in the same short transaction. A stale marker cannot clear a newer answer. The client reads the resulting check-in revision before a new send.

Normal recognition retries carry the acknowledged prior attempt ID. Only the server's existing reliability threshold or a completed assessment transcription-concern decision authorizes replacing that pending pointer. The old attempt is retained. This is distinct from ambiguous delivery: missing status, reliable pending evidence and unrelated revisions remain protected. No global under-three-word warning or confidence threshold is relaxed.

All short claim/fence transactions cap lock waiting at one second and SQL statement execution at five seconds, or keep an already stricter runtime timeout. These are transaction-local safety bounds in the local installer; no production pool/timeout setting or P2 delivery timeout is changed. A timeout leaves the outcome fenced for canonical recovery. Deploy the compatible client first and drain old browser tabs as well as unaware workers: legacy clients lacking recording identity receive a non-destructive 428, never an invalid-audio rejection. With retries disabled, the new client still supplies the same Blob-owned operation identity, independently of diagnostic telemetry.
