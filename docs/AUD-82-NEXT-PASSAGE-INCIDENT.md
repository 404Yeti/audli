# Incident 2026-10-24 10:20 UTC — "I couldn't get the next listening passage ready"

**Root cause (confirmed by logs and by reproduction):** `POST /api/lessons/{id}/exercise` failed with `psycopg.errors.UniqueViolation: duplicate key value violates unique constraint "lesson_exercises_pkey" — Key (exercise_id)=(26208248-…) already exists` raised from `attach_lesson_exercise` (`repository.py`) via `prepare_exercise` (`main.py`). The learner's latest exercise was unfinished and still linked to an earlier lesson that had ended; the new lesson tried to resume it, `INSERT`ed a second link for the same exercise (`exercise_id` is the primary key) and the whole transaction rolled back. `save_exercise` refuses to create a different exercise while the current one is unfinished ("Resume the current unfinished exercise"), so the lesson had no way forward: every retry hit the same error.

**Not** a timeout, model failure, Supabase latency, connection or latency-change problem: the request failed in 2.3 s with no generation step, the other 500+ requests of the window succeeded, no pool or provider errors exist, and the same failure reproduces on SQLite and PostgreSQL with default flags (no offload, lazy ping or other new flag).

**Evidence:** 29 consecutive `503`s on this one lesson between 10:20:36 and 10:26:20 UTC (client "Retry" loop: `lessons/start` 200 then `/exercise` 503 every ~5 s); each logged `Operation failed: Lesson exercise generation` with the IntegrityError (`Background on this error at … gkpj` is SQLAlchemy's IntegrityError page); no `ExerciseGenerator.generate` or TTS stage in the failing requests, so no passage was being generated (the existing exercise was being re-attached); no other 5xx anywhere from 10:20 to 11:40.

**User impact:** one learner (iPhone Safari) stuck at the start of the exercise phase for the rest of the lesson (about 6 minutes of the 10); lesson progress was intact (the failed transaction rolled back: revision, phase and links unchanged; `start`, `end` and `resume` kept working) but "Retry conversation" could never succeed. The message "your lesson progress is saved" was true; "Choose Retry" was misleading because the state could not recover by retrying. The real exception was logged server-side but the learner-facing message and the browser telemetry only show a generic 503.

**Predates the latency work:** the reuse-and-attach logic is from AUD-22 (2026-10-08) and the primary key from schema 001. It needs a learner whose previous lesson ended (time cap, expiry or completion) with its last exercise unfinished, then a new lesson: any learner can hit it. The first logged occurrence is today; I found no earlier one in the retained logs.

**Smallest safe fix (this PR, not merged):** `attach_lesson_exercise` resumes the unfinished exercise by **moving** its link to the new lesson when the previous owner is no longer open (idempotent when it is already this lesson's; refuses to take it from a lesson that is still open). One statement path, no schema change, no extra provider call; the old lesson's visible work is unaffected because only completed evidence is listed. Tests (`tests/test_stale_exercise_reuse.py`, SQLite and PostgreSQL): the incident scenario now succeeds, one link per exercise, idempotent retry, never taken from an open lesson, unattached and lesson-free exercises behave as before; four of them fail without the fix.

**Follow-ups (separate):** make the lesson-exercise endpoint's 503 distinguish a non-retryable state error from a transient failure, and report the HTTP status in the browser telemetry; clean up or complete an unfinished exercise when its lesson ends.
