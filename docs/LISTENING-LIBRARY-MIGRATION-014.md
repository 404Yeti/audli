# Migration 014 (curated library): safety review, deployment and rollback runbook

Status: **not applied.** Apply only after the owner approves in writing. Prerequisites: PR #150 (hardening) and PR #151 (browsing) merged, so the SQL below is final and the app reads categories safely.

## 1. What it does (and does not)
* Adds **one table**, `listening_library_entries` (workflow record: state, category, reviewer, review digest, timestamps). Records itself as version 14 in `listening_migrations`.
* Alters **no existing table**, touches no 1.x table and not `schema_migrations`. Independent of 013 (account erasure, still unapplied).
* RLS enabled, all privileges revoked from `PUBLIC`/`anon`/`authenticated`. The API role gets **SELECT only** (through the conditional block in `docs/postgres-listening-api-role.sql`); only the database owner (the operator CLI) writes it.
* Foreign keys: `lesson_id` and `version_id` are `ON DELETE CASCADE`; `curator_id` is `ON DELETE SET NULL` (index `listening_library_by_curator`).
* Visibility is unchanged: **a lesson with no owner row is shared**. The table never decides who can see a lesson.

## 3. Before applying
1. Owner approval recorded (Linear AUD-113 comment).
2. PRs #149 (into #138), #150 and #151 merged; production deployed and healthy (`/api/health` 200).
3. Confirm the ledger: `SELECT version FROM listening_migrations ORDER BY 1;` must be exactly `9,10,11,12` (013 absent unless separately approved and applied).
4. **Backup** (recovery point). Supabase: confirm the daily backup / point-in-time recovery window covers now and note the timestamp; additionally take a logical backup of the 2.0 tables:
   `pg_dump "$OWNER_URL" --no-owner -t 'listening_*' -f listening-pre-014-$(date -u +%Y%m%dT%H%M%SZ).sql` (stored privately; it contains learner data, so treat it as such and delete it after the verification window).
5. Pick a quiet time. The migration takes a short exclusive lock on `listening_migrations` only (`lock_timeout 5s`, so it fails fast rather than waiting).

## 4. Apply
Apply **only** `docs/postgres-014.sql`, as the database owner, in one session:
`psql "$OWNER_URL" -v ON_ERROR_STOP=1 -f docs/postgres-014.sql`
Do **not** use `python -m scripts.migrate_postgres --listening` unless you have confirmed it would apply only 014 (it applies every pending listening migration in order, which would include 013 once that is added to the list). The script refuses a second run ("already applied or partially present"), so a repeat cannot damage anything.
Then re-run the API-role SQL (idempotent, conditional): `psql "$OWNER_URL" -f docs/postgres-listening-api-role.sql`.

## 6. Rollback and recovery
Nothing reads the table except the catalog category lookup, which tolerates its absence, so rollback is safe at any time **before the first lesson is published**:
```sql
BEGIN;
DROP TABLE listening_library_entries;
DELETE FROM listening_migrations WHERE version = 14;
COMMIT;
```
Order matters if lessons have been published: **first** `python -m app.listening.library unpublish <lesson>` for each published lesson you want private again (publishing removed their owner rows; dropping the table alone leaves them shared, still playable, but with no review record). Dropping the table loses the review audit trail, so export it first: `SELECT * FROM listening_library_entries` to a private file.
Full recovery from the backup is needed only for data corruption, which this additive change cannot cause. 2.0 as a whole is removed with `postgres_listening_rollback()`, which already lists this table.
No application rollback is required for the migration alone. If PR #151 must be reverted, revert the PR; the table can stay.

## 7. Operating the workflow (after approval, for the curator)
Set `AUDLI_LISTENING_CURATOR_IDS=<your account id>` **in the operator's shell only** (the API never reads it). `python -m app.listening.library status | review ID | register ID --category C | approve ID --reviewer NAME | publish ID | unpublish ID`. Each step prints what it did or `Refused: <reason>` and changes nothing on refusal.
